# Meteor Detector

The Meteor Detector channel is intended for RF meteor-scatter trail monitoring. It channelizes the selected receiver offset and resamples the channel to 100, 300, 1000, or 3000 Hz. The GUI displays the same resampled IQ in two independently configurable waterfalls. The trail-echo view defaults to a 1024-point FFT with 50% overlap for frequency resolution, while the head-echo view defaults to a 128-point FFT with 75% overlap and faster updates for time resolution.

The Geometry rollup records the radar transmitter latitude, longitude, beam azimuth, elevation, azimuth beamwidth, and elevation beamwidth, plus the receive antenna azimuth, elevation, and HPBW. Receive pointing can be entered manually or synchronized once per second from a selected GS232Controller feature. Selecting no rotator restores manual receive azimuth and elevation entry. The current receive pointing and beamwidth are included in exported RMOB reports.

The map button sends translucent transmitter and receiver beam volumes to open Map features, together with their geometric intersection. The orange TX and cyan RX solids are capped at the selected maximum altitude, which defaults to 1000 km. Their brighter green overlap is the region inside both antenna beam envelopes; it is a geometric coverage volume rather than a received-power or radar-sensitivity prediction. The 2D map displays corresponding footprints. The GRAVES defaults use approximately 180 degrees of azimuth beamwidth across the southern sky and 25 degrees of elevation beamwidth. A zero azimuth or elevation beamwidth leaves that antenna pattern unspecified and suppresses its volume.

Detected Doppler sweeps are listed in the Satellites tab. Alongside signed center-Doppler speed, the table reports maximum absolute equivalent radial speed from the fitted sweep endpoints and average Doppler drift rate. An RF-only classification combines endpoint speed, drift rate, total frequency excursion, and track duration into Aircraft, Satellite, or Uncertain, with a heuristic satellite score. The score is not a calibrated probability.

When an ADS-B Demod channel is open, fresh aircraft position, altitude, ground speed, track or heading, and vertical-rate reports are converted to source-neutral moving-target states; the fields must also be sampled close to the position report's own time, and a state whose direction comes from heading rather than measured track is slightly down-weighted in scoring. The matcher extrapolates each state through the sweep interval, predicts the bistatic Doppler at the sweep start and end times from the configured transmitter and receiver positions, and scores the observed center and drift residuals.

Satellite matching uses the same prediction and scoring path. A plugin-local worker thread downloads the CelesTrak active OMM CSV catalog plus supplemental visual, analyst, recent-launch, GEO protected-zone, potential-decay, FENGYUN 1C, IRIDIUM 33, and COSMOS 2251 element sets. The CelesTrak SATCAT CSV supplies canonical names and object types and filters objects already marked as decayed. The Satellites information dialog can also configure a Space-Track login; when configured, the worker authenticates to `space-track.org` and downloads its comprehensive GP 3LE set. The password can be retained in local application settings but is never included in Meteor presets or WebAPI data. All files are cached under the application's `meteor` data directory and refreshed when their cache is older than a day. CelesTrak rejects repeated requests for the same file within two hours of a successful download, so this minimum interval is enforced even for an explicit refresh. Public CelesTrak sources use HTTP conditional requests so unchanged files are not re-downloaded and remain a fallback when Space-Track is not configured or unavailable. Overlapping element sets are deduplicated by NORAD catalog ID and the newest epoch wins. SATCAT alone is not propagated because it does not contain a complete orbital state. The OMM CSV and Space-Track 3LE adapters preserve six-digit/Alpha-5 NORAD catalog IDs while converting the orbital fields for the bundled SGP4 propagator. SGP4 propagation, maximum-altitude, horizon, and configured TX/RX beam filtering, and matching all run on that worker. Geometric culling snapshots are shared by detections in the same five-second interval to keep accelerated file replay responsive; the horizon and beam tests are padded by a margin so a fast mover near an edge at the snapshot instant is not lost. Each candidate that survives culling has its Doppler evaluated by SGP4 propagation at the sweep's own start and end times, so orbital curvature is included in the predicted drift rather than extrapolating a single velocity. The information button on the Satellites tab shows loaded object categories and exclusive rejection counts for the latest matching snapshot. Live sources use the detection's system UTC; FileInput and SigMF FileInput use the recording time from the device report, corrected for detection age and accelerated playback. The best ADS-B, TLE, and lunar results are ranked together; a row is identified as `Aircraft (ADS-B)`, `Satellite (TLE)`, or `Moon` only when its score is at least 60 and leads every other candidate by at least 8 points. Otherwise the RF-only class remains and the Match cell lists the best candidate plus up to three alternatives within that eight-point ambiguity margin; its tooltip includes their scores and residuals. TLE matches are unavailable in builds where the SGP4 library was not found.

The matching-statistics dialog also compares the local system clock with Cloudflare's public anycast NTP service. Five SNTP probes run on the matcher worker every 30 minutes and when stale statistics are requested. The estimate uses up to the three probes with the lowest network delay; its displayed uncertainty includes path delay, variation between the selected probes, and the server's advertised dispersion. This normally provides millisecond-scale accuracy and a much tighter assessment than an HTTP timestamp. If UDP port 123 is blocked, the worker falls back to the HTTPS `Date` reported by Google's lightweight connectivity-check endpoint; that fallback has whole-second resolution and therefore reports a substantially larger uncertainty. The result is acceptable when the complete estimated error interval lies within one second, not acceptable when it lies wholly outside one second, and inconclusive when it crosses the limit. This is a diagnostic rather than a clock setter: configure the operating system to synchronize its clock when moving-target matching is required.

The same worker also evaluates the Moon using SDRangel's built-in lunar ephemeris. `Moon possible` is true only when the Moon is above the transmitter and receiver horizons and inside both configured antenna beams at the detection midpoint. The table then shows the expected bistatic center Doppler offset and its change over the detected sweep, calculated from the changing transmitter-Moon-receiver path length at the recording time. A sufficiently close, unambiguous Doppler fit is identified as `Moon`; the prediction remains visible even when another moving target is a better match.

## Frequency calibration

Accurate receiver frequency calibration is important for moving-target matching. Meteor and sweep detection can operate with an uncalibrated receiver, and a constant receiver error does not change the measured Doppler drift, but it shifts every reported center frequency and signed radial speed. TLE, ADS-B, and lunar identification compare the measured absolute Doppler with a prediction, so even a visually convincing sweep can remain unmatched when the receiver frequency offset is too large.

The frequency error in parts per million is:

```text
error_ppm = measured_error_hz / reference_frequency_hz * 1000000
```

At the 143.050 MHz GRAVES frequency, 1 ppm is approximately 143 Hz, 0.2 ppm is approximately 29 Hz, and 0.1 ppm is approximately 14 Hz. The matcher can use a center-frequency scale as small as 25 Hz for narrow events, so calibration to 0.2 ppm or better is recommended at GRAVES, with 0.1 ppm preferred for reliable target discrimination. At the approximately 50 MHz BRAMS and GB3MBA frequencies, 0.2 ppm is approximately 10 Hz.

Before calibrating an RTL-SDR or another temperature-sensitive receiver, allow it to warm up for at least 20 to 30 minutes in its normal operating position. Tune to a stable signal with an accurately published frequency, such as a suitable amateur beacon (for example GB3VHF), a frequency-disciplined cellular carrier, or a GPS-disciplined signal generator. Use a narrow, averaged spectrum to measure the error, then adjust the receiver's frequency correction until the reference appears at its published frequency. A reference reasonably close to the meteor-radar frequency is preferable. Ordinary broadcast FM stations are generally unsuitable as precision references.

Repeat the check after the receiver has been running for a while and whenever its ambient temperature changes substantially. Calibration corrects the initial oscillator error, but inexpensive oscillators may continue to drift with temperature. When recording IQ for later FileInput replay, calibrate before recording and retain the applied correction with the recording notes; replay cannot recover an unknown frequency error from the IQ data alone.

The radar's direct carrier is the best in-band reference when it is receivable because it also removes any transmitter-frequency offset. At distant receiving sites the direct carrier may be below the noise floor, in which case calibration against an external beacon or disciplined source is still valuable. Residual transmitter error and propagation effects can then remain as smaller contributions to the target-match residual.

## Detection

Detection operates on a two-dimensional spectrogram image rather than per-frame heuristics. Frames of about 125 ms (clamped to 32–256 samples, hopping every quarter frame) are zero-padded to twice the frame length before the FFT, giving finer frequency bins than the frame alone would allow. Columns accumulate in a rolling 20-second analysis window, and the per-bin noise floor is the median power across that window: a median is non-adaptive over the window, so a meteor's faint decay tail cannot raise the floor and mask itself. The excess-over-floor image is segmented by hysteresis: pixels at least 11 dB above the floor seed components (isolated specks are discarded), which then grow through all connected pixels at least 6.5 dB above the floor, capturing faint tails. A short vertical morphological close heals single-bin splits, and temporal fragments that continue one another's frequency drift within a tight envelope are linked into a single event.

A blob is accepted as a meteor when its integrated power — the sum of excess above the grow threshold over all its pixels — reaches the sensitivity threshold (the **Sens** setting; lower is more sensitive), its brightest pixel is at least 16 dB above the floor (faint spread noise can accumulate score over area but never gets bright), it does not occupy most of the band in any column (broadband impulses), and its frequency track is not an elongated, highly linear drift (satellite sweeps; meteor tracks are vertical or irregular). A frame-wide distributed-impulse gate also rejects disconnected components that share one instant with substantial seed energy spread across most of the monitored band. There is no machine-learned classifier: acceptance is one calibrated threshold plus these vetoes. The defaults were calibrated against several hundred manually reviewed detections.

The rolling window is re-analysed every half second and a blob is reported as soon as it is provably complete — its last column is far enough behind the live edge that no later column could extend it — so detections appear on the display about a second after the echo ends. Reported times and durations include the STFT frame support on both ends. The frequency box hugs the bright core of the blob rather than its faint skirt, deliberately, following visual review of box quality. Frequency drift is the fitted slope of the blob's frequency track multiplied by its duration. The maximum duration setting clips longer reports and marks them truncated; events longer than roughly the analysis window cannot be measured intact.

## Satellite sweeps

Blobs rejected by the sweep veto are not discarded: they are consolidated along their common Doppler drift line into a single satellite detection per pass. Each fragment contributes both ends of its fitted trajectory to the running least-squares line, preserving drift even when fragments overlap in time. Fragments join when the line predicts their frequency within tolerance, and overlapping active tracks with compatible slopes are coalesced before reporting. Faint below-threshold linear segments that continue an established line extend it, and when a pass completes, the detector walks the fitted line outward through chained faint dashes to cover the dashed leading and trailing parts of the track. Two consolidated sweeps that continue one another — a pass whose fast, faint mid-section was invisible — are merged rather than reported twice.

An otherwise-accepted, short diagonal blob can be the first visible part of a later satellite pass. Such candidates are held briefly; if a subsequent sweep has the same slope direction, a compatible slope, and the predicted frequency at the candidate, the candidate is retrospectively adopted into that sweep instead of being reported as a meteor. Other detections remain in chronological order while this decision is pending. An accepted blob lying on an already-established sweep's line near the sweep's own time span is likewise counted as part of the sweep, not as a meteor.

## Regression harness

The standalone `meteor_demod_sink_test` harness replays stereo 16-bit IQ WAV recordings through the full channel:

```text
meteor_demod_sink_test --wav recording.wav --channel-sample-rate 3000 --details
```

Run without arguments it executes the regression fixtures in `test/tests`: each `name.csv` lists the expected detections for `name.wav` (time, duration, center frequency, span, drift, total power), compared within tight tolerances. A fixture named `name@3000.csv` runs the same recording at a 3000 Hz channel rate, so both calibrated rates are covered. Expectation CSVs may append a `required` column; optional rows describe genuinely ambiguous cases that may be absent but must match if present.

The harness accepts repeated `--tunable name=value` overrides for any `DetectorTunables` member (names drop the `m_` prefix), for example `--tunable blobScoreThreshold=100`, allowing operating points to be swept against recordings without rebuilding.

The detection algorithm is an exact port of the offline reference implementation in `test/detector2d/blobs.py`, verified by a golden-fixture parity test in `test/detector2d/cpp`. The research tooling under `test/detector2d` (offline detection, review rendering, and the browser-based labeler in `test/label_candidates.py`) was used to calibrate the acceptance threshold and box shaping and remains usable for future corpus work.
